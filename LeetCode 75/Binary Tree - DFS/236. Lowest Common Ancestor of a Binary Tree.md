# Claude notes

Your approach works in principle: find the root-to-node path for each of p and q, then walk both paths together until they diverge. But there are some correctness issues and a much simpler solution.

Issues in your current code

1. The backtracking logic is fragile. You decide whether to pop with path[path.length - 1] != q. That only tells you whether q happens to be on top of the stack, and it breaks down in a few cases:

After the left recursion finds q, you still call findPath on the right subtree. The guard path[path.length-1] == q at the top protects you, but only by accident of ordering.
The early return if (root.left == null && root.right == null) return; skips the push but also skips the pop logic, so it only works because leaves never get pushed. It’s easy to break when editing.
Comparing the stack’s top to q is an indirect way of asking “did I find it?” A boolean return value says that directly.

2. shift() is O(n) per call. Array shift() re-indexes the array, so the while loop is O(n²) worst case. Use an index instead.

3. Dead code. let n = stack1[0] is only meaningful because both paths start at root; the null checks on p/q are unnecessary given LeetCode’s constraints (both exist in the tree).

4. Cleaner path finder. Return a boolean:

ts
function findPath(node: TreeNode | null, target: TreeNode, path: TreeNode[]): boolean {
if (!node) return false;
path.push(node);
if (node === target) return true;
if (findPath(node.left, target, path) || findPath(node.right, target, path)) return true;
path.pop(); // backtrack: target not under this node
return false;
}

function lowestCommonAncestor(root: TreeNode | null, p: TreeNode | null, q: TreeNode | null): TreeNode | null {
const pathP: TreeNode[] = [];
const pathQ: TreeNode[] = [];
findPath(root, p!, pathP);
findPath(root, q!, pathQ);

    let lca: TreeNode | null = null;
    for (let i = 0; i < Math.min(pathP.length, pathQ.length); i++) {
        if (pathP[i] !== pathQ[i]) break;
        lca = pathP[i];
    }
    return lca;
}

This is O(n) time and O(h) space (O(n) in the skewed case). It’s a clean version of your idea.

The optimal approach: single-pass recursion

Instead of finding two paths and comparing, ask each node: “do p and q live in my subtrees?”

ts
function lowestCommonAncestor(root: TreeNode | null, p: TreeNode | null, q: TreeNode | null): TreeNode | null {
if (!root || root === p || root === q) return root;

    const left = lowestCommonAncestor(root.left, p, q);
    const right = lowestCommonAncestor(root.right, p, q);

    if (left && right) return root; // p and q are on different sides
    return left ?? right;           // both on one side (or neither)
}

Why it works:

If the current node is p or q, return it. The other node is either below it (so this is the LCA) or elsewhere (and the parent will sort it out). That covers the “node is an ancestor of itself” rule.
Recurse into both children. Each call returns a node if it found p or q in that subtree, else null.
If both sides returned something, p and q are split across this node, so it’s the LCA.
If only one side returned something, pass it up. It’s either the LCA already found deeper, or just a single target found.

Time is O(n), space is O(h) for the recursion stack, and there’s no path bookkeeping or backtracking.

Thought process: how to get there
Start with the brute-force idea you had. Path-to-root comparison is a legitimate first answer, and in an interview it’s good to say it out loud.
Ask what the two paths really encode. The LCA is the last shared node, i.e., where the paths diverge. That is the same as “the node where p and q first end up in different subtrees.”
Turn that into a per-node question. If you can answer “did I find a target in my left/right subtree?” at each node, the divergence point falls out of the recursion with no extra data structure.
Handle the edge case by reading the problem. A node can be its own ancestor, which is exactly why returning early when root === p || root === q is correct.
General pattern to remember. When you’re storing a path just to compare it later, check whether a post-order return value can carry the same information. This shows up in diameter of a tree, max path sum, and balanced-tree checks.
Minor style notes
Use === consistently (you mixed == and ===).
Prefer Node | null guards at the top of a recursive helper rather than checking children before recursing; it removes the root.left && ... clutter.
Name things for intent: pathP/pathQ instead of stack1/stack2, since they’re root-to-node paths, not true stacks in use.
